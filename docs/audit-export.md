# Audit export

Unofficial DagzTagz project. Not an xAI, SpaceXAI, or Grok product. This runtime does not call the Grok API. The roles this tool does not fill are in [getting-started.md](../getting-started.md#what-this-tool-is-not).

An audit folder is the packet this program writes when you ask it to show its work. You can hand the folder to someone else. They can read what was checked without your chat, and without your private key.

```bash
vesper --workspace ./workspace export --audit ./out
```

The folder itself is mode `0700`: only your user can list it. Each file inside is mode `0600`: only your user can read it. On a shared computer, another normal account should not be able to open them.

Run `vesper verify --head` first. Export can still print `ACCEPT` when your own snapshot was not copied. The tables below say how to see that.

## The six files

| File | What you are looking at | A good copy | A problem |
|------|-------------------------|-------------|-----------|
| `plan.md` | The checklist the export promised to run. The wording is the same on every run. It is written before the results. | The sections `Promised`, `Quit-early`, and `Result` are all there. | The file is missing, or someone edited the promises after the run. |
| `evidence.md` | A transcript. Each command is shown with its exit code and the text it printed. | You can see the test suite, the forged sample, and the key-permission check. | A command is missing, or its exit code disagrees with `score.json`. |
| `critic.md` | A short review under six fixed headings. | `VERDICT` is `ACCEPT`. `BLOCKERS`, `MISSING EVIDENCE`, and `WAIVERS` each say `none`. | `VERDICT` is `REJECT`, or a heading is missing. |
| `score.json` | The same result, written so a program can read it. | `"pass": true` and `"waivers": []`. | `"pass": true` while `critic.md` says `REJECT`. Do not edit this file to change the answer. |
| `state_hash.txt` | One line. It is a fingerprint of the notes file at the moment of export. The fingerprint is SHA-256 of the notes in canonical form: one standard spelling of the JSON, with no extra spaces. | One 64-character hex line, then a newline. | The line is empty, or a later fingerprint of `state.json` does not match it. That means the notes changed after the export. |
| `fork_verified.json` | A copy of your latest signed snapshot, or the JSON value `null`. The snapshot is the saved notes plus the signature. It is not the chat that produced them. | After `verify ok`, the file matches `workspace/forks/<name>.json` byte for byte. | The file is `null` when you expected your snapshot, or it contains the private key. |

## What `plan.md` promises

| Promise, in the file | What it is asking the export to prove |
|----------------------|----------------------------------------|
| Heal the drifted sample, or reject a document that has no character id | A notes file that is only missing lists can be filled in. A file that does not say whose notes they are is refused, and left unchanged. |
| Sign a real snapshot and check the parent link | A second snapshot can name the first one. A false parent link is rejected. |
| Reject the forged sample | `fixtures/forged-fork.json` is a bad signature. The export must not accept it. |
| Enforce mode `0600` on the private key and mode `0700` on the identity directory | The secret file is readable only by you. The key folder is listable only by you. A file that is mode `0644` is refused and is not quietly repaired. |
| Age a note with a clock the export sets | Moving the clock forward changes the note's weight. Using the note's own time as the clock does not. That second run is the control. |
| Reject path tricks in names | A name that contains `..`, a slash, or an absolute path is rejected. |
| Write this folder without key material | The private key is not in the folder. |

`Quit-early` means a green test suite is not enough on its own. The suite must have opened the forged sample, moved the clock, and checked the key mode. `evidence.md` has to show those commands.

`Result` means `score.json` is filled from those checks, and only after `evidence.md` exists.

## What the `critic.md` headings mean

| Heading | On a clean run | When it is not that |
|---------|----------------|---------------------|
| `BLOCKERS` | `none` | A check failed. The names here match the checks that are `false` in `score.json`. The verdict is `REJECT`. |
| `RISKS` | Two standing notes. The short key id only names a key; the signature is the real check. Sleep rounds a weight to 10 decimal places. | These notes are limits of this version. They do not fail the run. |
| `NITS` | Two standing notes. Graph links store the two ends in sorted order. The secret search is recorded as an exit code, not by pasting the pattern into this folder. | Small notes. They do not fail the run. |
| `MISSING EVIDENCE` | `none` | In this version the line stays `none`. A missing command shows up as a failed check instead. |
| `WAIVERS` | `none` | A recorded exception, with an id and a reason. A clean walk has none. |
| `VERDICT` | `ACCEPT` | `ACCEPT WITH WAIVERS` when every check passed and a waiver was recorded. `REJECT` when a check failed. The success word `ACCEPT` does not contain the letters `REJECT`. |

## What `score.json` contains

The fields are written in this order.

| Field | What it is |
|-------|------------|
| `task_id` | Always `001-heal-or-die`. That is the checklist in [tasks/001-heal-or-die.md](../tasks/001-heal-or-die.md). |
| `pass` | `true` only when every check below is `true` and the test suite exits 0. |
| `checks` | The seven yes/no results, in the order in the next table. |
| `waivers` | A list. A clean run is `[]`. |

| Check name | What it is proving | `true` means |
|------------|--------------------|--------------|
| `schema_heal_or_reject` | The drifted sample is refused. A copy can be repaired without changing who it belongs to. A file with no identity is refused and not written. | All three of those happened. |
| `forged_signature_rejected` | The forged sample is a bad signature. | The transcript contains `EXIT:2`, and the reason is `bad_signature`. |
| `parent_chain_ok` | A temporary workspace can sign two snapshots in order. A lied parent link, a missing parent, and an old file saved under a new name are rejected. | All of those trials passed. |
| `key_mode_enforced` | Your key folder and secret file have the private modes, and a world-readable key file is refused without being repaired. | The directory is mode `0700`, the secret is mode `0600`, and a mode `0644` test file stayed `0644`. |
| `memory_decay_ran` | Aging is real, and a clock that does not move is not treated as aging. | A weight of `1.0` stays `1.0` when the clock equals the note's time, and becomes smaller ten hours later. |
| `path_traversal_rejected` | Names cannot point outside the workspace. | Every sample that contains `..`, a slash, or an absolute path was rejected. |
| `no_secrets_in_export` | The folder you are reading is safe to hand over. | The search found no private-key file and no private-key text. |

When you run export from the terminal, it also runs `python -m pytest -q`. `pass` stays `true` only if that command exits 0. If export is already running inside the test suite, it does not start a second one. A test run that export itself starts is marked with the environment name `VESPER_EXPORT_CHILD`, set to `1`. Nothing else in this version reads that name.

The terminal prints the same verdict as `critic.md`. Success is `ACCEPT` or `ACCEPT WITH WAIVERS`, then the folder path, exit 0. Failure is `REJECT`, then `vesper: audit checks failed`, exit 2.

These seven checks run on sample files and on temporary folders. They do not, by themselves, prove that your personal snapshot was copied into `fork_verified.json`.

## What must not be in the folder

| Must not appear | Why |
|-----------------|-----|
| A directory named `identity` | That directory holds the private key. Export does not copy it. |
| A file ending in `.priv`, including `edcsa-p256.priv` | That is the private key. The spelling `edcsa` is the v0.1 filename. |
| A file named `hmac.key` | That is the other form of the private key, used only when the ECDSA package did not import. |
| Text shaped like a private key | A snapshot that contains that text is not safe to hand over. |

If the snapshot that would have been copied contains that text, export replaces `fork_verified.json` with the word `null`, marks `no_secrets_in_export` false, and leaves `pass` false. The transcript says `secret-marker scan found a hit; the fork copy was withheld`. It does not repeat the secret text. A search with no hits exits 1. That exit code is the passing result for the search.

The exact search text lives in [tasks/001-heal-or-die.md](../tasks/001-heal-or-die.md), in the block tagged `scorer-contract`. Do not copy that search into the audit folder. The folder would then match its own notes.

When your notes folder is literally named `workspace`, one transcript line is `stat -c '%a' workspace/identity/*`. Those numbers are file modes, not key bytes.

The forged-sample line in the transcript is exactly:

```text
vesper verify fixtures/forged-fork.json; echo EXIT:$?
```

Its printed output must contain `EXIT:2`. For that sample, exit 2 means the bad signature was rejected.

## The saved example

[examples/passing-audit/](../examples/passing-audit/) is one successful export kept in the repository. It contains a public key and a signature. It does not contain a private key.

The snapshot inside it is named `alpha` in the JSON. The file on disk is named `fork_verified.json`. `vesper verify` compares the filename with the name inside the signature, so checking that path reports `name` and exits 2. That report is the filename rule, not a bad signature. Check `workspace/forks/alpha.json`, or copy the example to a file named `alpha.json`, and the signature can be checked from the public key inside the file.

The test transcript in that example says `58 passed`. That number is from the day the example was saved. It is not today's count. Do not rebuild the example just to change the number. A new export belongs in `out/`, which git ignores.

## Command

```bash
vesper --workspace ./workspace verify --head
vesper --workspace ./workspace export --audit ./out
find out -name 'edcsa-p256.priv' -o -name 'hmac.key' -o -name 'identity'
```

What good looks like: `verify ok`, then `ACCEPT`, then the `out` path, exit 0. `out/score.json` has `"pass": true` and `"waivers": []`. `find` prints nothing. `fork_verified.json` is a copy of your snapshot, not `null`.

What failure means: `REJECT` and exit 2. Open `out/evidence.md` and read the command whose exit code is unexpected. If the secret search withheld the snapshot, `fork_verified.json` is `null` and the score stays failed on purpose.
